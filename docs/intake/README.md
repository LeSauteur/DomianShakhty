# Ежедневная публикация: один пакет → один PR

`scripts/intake.mjs` добавляет объекты и агентов в существующий статический сайт. Сам инструмент **не выполняет Git-команды публикации**. Планирование не меняет каталог; `--out` сохраняет только явно запрошенный отчёт в игнорируемом `artifacts/`.

## Входной пакет

JSON, UTF-8, `version: 1`, уникальный `id` партии. Пути к архивам, папкам и портретам считаются относительно файла пакета. Пример структуры:

```json
{
  "version": 1,
  "id": "agent-yyyymmdd",
  "approval": {
    "confirmed": false,
    "date": "2026-11-24",
    "note": "Указать реальное поручение пользователя; пример не является разрешением"
  },
  "agents": [],
  "listings": [{
    "source": {
      "id": "gmail-message-id",
      "from": "Имя Фамилия <sender@example.org>",
      "text": "Полный исходный текст письма",
      "attachments": [{"filename": "front.jpg", "size": 123456}]
    },
    "record": {
      "type": "house-secondary",
      "format": "secondary",
      "title": "Дом 50 м² — пример формата",
      "location": "unspecified",
      "address": "Адрес уточняется",
      "area": 50,
      "description": "Описание на основании письма",
      "features": ["50 м²"]
    },
    "media": {
      "archive": "photos.zip",
      "order": ["front.jpg"],
      "cover": "front.jpg"
    }
  }]
}
```

- Вместо `archive` допускается `directory`, одновременно оба нельзя. `order`, если задан, перечисляет **все** исходные фото ровно один раз. `cover` перемещает выбранный файл на первое место. JPEG, PNG, WebP; ZIP распаковывается в памяти с ограничением размеров и защитой путей. Битое фото останавливает всю партию.
- `source.attachments` необязателен, но для почтового импорта обязателен по рабочей инструкции: размеры берутся из Gmail `size_bytes`, а не вычисляются заново как замена проверке письма. Файлы сверяются по точным именам и размерам.
- `record` использует поля `src/data/listing.schema.json`. ID создаётся автоматически по типу и следующему свободному номеру; явный ID тоже проверяется. `image`, `gallery`, `verified*` и телефон в `record` запрещены: их задаёт конвейер/существующий сайт.
- Агент определяется по email отправителя в `team.json`. Для ручного назначения или пересылки от другого сотрудника нужны `record.agentId` и `agentAssignmentNote` с основанием из письма/уточнения пользователя. Например, письмо Левковец «объект Семутенко» относится к Семутенко. Старые объявления не переназначать автоматически.
- Цена — целое число рублей; также принимаются строки `6,3 млн`, `6300 тыс`, `6 300 000 ₽`. Неоднозначные сокращения вроде `6.3` CLI отклоняет: сначала нормализовать по подтверждённому контексту письма/пользователя и сохранить исходник. Без цены поле `price` **отсутствует**, не равно нулю.
- Неизвестные площадь/комнатность отсутствуют. Если не указан населённый пункт, `location: "unspecified"`, в `address` явно написать, что уточняется; известные ориентиры сохранить. Ничего не подставлять по умолчанию в Шахты. Противоречия сохранять в `contentIssues`, не выбирать удобное значение.
- Для нового агента добавить `agents: [{record: {...}, portrait: "portrait.jpg"}]`. Обязательны `name`, `shortName`, `firstName`, `role`, `lead`, `phone`, `phoneHref` (`tel:+7…`), непустые массивы `directions`, `skills`, `serviceAreas`; email, если есть, должен быть корректным. `id/slug` можно задать одинаковыми или получить из имени автоматически. Портрет и варианты 360/640/960 создаются без увеличения исходника. Новый агент может получить объект в том же пакете.

## План и применение

В новом worktree сначала выполните `npm ci` один раз. Повторная установка той же партии нужна при изменении lock-файла или ошибке установки. После применения данных выполняется полный `npm run qa`.

```powershell
npm run intake -- plan --batch artifacts/batch.json --out artifacts/intake-plan.json
# Проверить added, agentId, price, photoCount, warnings, changedFiles и token.
$intakeToken = (Get-Content artifacts/intake-plan.json -Raw | ConvertFrom-Json).token
npm run intake -- apply --batch artifacts/batch.json --token $intakeToken --out artifacts/intake-applied.json
```

`apply` разрешён только в отдельной ветке `codex/` с чистыми каталогом, командой, медиареестром и изображениями; чужие незакоммиченные изменения блокируют запись. Требуются `approval.confirmed: true` с реальным основанием и повторное вычисление плана. Изменение входных файлов или каталога меняет token. Существующие записи сохраняются без изменений, включая порядок и контакты; хешируются используемые изображения, сохранённые прежние обложки из медиареестра и конфигурация сайта. На экран выводится краткий отчёт; полный список файлов остаётся в `--out`, либо выводится с `--verbose`.

Дубли проверяются по ID, письму, названию, адресу с параметрами и хешам нормализованных фотографий. Это кандидаты на ручную проверку, а не доказательство совпадения по одному адресу. Автоматически перезаписывать или обходить блокировку нельзя. Проверка не распознаёт все изменённые/обрезанные копии фотографий и не заменяет просмотр исходных писем.

Запись защищена lock и журналом; при обычной ошибке новые файлы удаляются, JSON восстанавливаются. После аварийного завершения процесса `.intake.lock` / `.intake-transaction.json` требуют проверки процесса и журнала перед продолжением. Не удалять их вслепую: журнал содержит резервные JSON и перечень новых файлов. Сначала сохранить копию, сверить каталог и восстановить конкретную незавершённую операцию.

В Git идут каталог, WebP и компактный `docs/intake/<batch-id>.json` с источником, агентом и хешами изображений. Исходники, подписанные ссылки скачивания и рабочие отчёты остаются в `artifacts/`, не в коммите. Применение не равно публикации: затем обязательны успешный `npm ci` перед работой, полный `npm run qa`, просмотр diff и штатный PR-процесс из AGENTS.md.

## Ожидание GitHub без повторного исследования

```powershell
npm run wait:checks -- <PR>
npm run wait:deploy -- <полный-merge-SHA>
```

Первый вызов оборачивает один `gh pr checks --watch --interval 10`. Второй находит только `pages.yml` для точного merge SHA в `main` (не более десяти попыток с паузой в минуту), затем выполняет один `gh run watch --exit-status --interval 30`. Вывод сохраняется в `artifacts/github-*.log`. Не запускать рядом циклы `gh run list` и повторные проверки. При ошибке открыть конкретный `--log-failed`, исправить причину; не повторять merge/push вслепую.

## Проверка инструмента

```powershell
npm run intake:test
npm run intake:replay -- --archives <папка-с-54.zip-59.zip-_3.zip>
```

Replay читает фиксированный предшествующий коммит PR №67, создаёт временную копию, добавляет три исторических объекта и сверяет факты, агента, порядок и побайтовые хеши всех 17 фотографий. Проверяет сохранность прежнего каталога и отказ повторного импорта. Действующий каталог не меняется. Отчёт: `artifacts/replay-pr67.json`. Архивы в репозиторий повторно не добавляются.
